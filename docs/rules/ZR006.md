# ZR006 — patch-stack

## Why

A tower of `@patch` decorators is a design smell: the test is lashing a
unit to its dependencies' internals by string-path, and each patch
layers on another thing the reader has to track. Tests with four, five,
six patches usually mean the code under test has poor seams. Prefer
dependency injection, a single fixture, or a fake object passed in.

The rule counts `@patch`, `@patch.object`, and `@mock.patch` decorators
on a test function and fires when the count strictly exceeds
`max_patches`.

## Positive example

```python
from unittest.mock import patch

@patch("app.db.connect")
@patch("app.cache.get")
@patch("app.logger.info")
@patch("app.clock.now")          # 4 patches > default 3: ZR006 fires
def test_complex(a, b, c, d):
    ...
```

## Negative example

```python
def test_simple(fake_clock, fake_db):
    service = Service(clock=fake_clock, db=fake_db)
    assert service.run() == "ok"
```

## Config

```toml
[tool.zorilla.rules.ZR006]
enabled = true
max_patches = 3
```

`max_patches` defaults to `3` — the rule fires on the 4th patch decorator.

## Suppression

Inline, on the line of the **first** `@patch` decorator — that is where
the finding points; a directive on the `def` line has no effect:

```python
@patch("a")  # zorilla: ignore[ZR006] -- legacy seam, fixture tracked in #12
@patch("b")
@patch("c")
@patch("d")
def test_legacy(a, b, c, d):
    ...
```

If that decorator spans several lines, any line of it works.

File-level:

```python
# zorilla: ignore-file
```
