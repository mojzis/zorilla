# ZR001 — conditional-test-logic

## Why

A pytest test should read as a linear "arrange / act / assert".
Control-flow constructs (`if`, `for`, `while`, `try`, `match`) hide
intent, invite coverage holes, and often smuggle two scenarios into one
test. Extract the branches into parametrized cases
(`@pytest.mark.parametrize`) or separate test functions.

The rule fires once per test function whose body contains any
`if_statement`, `for_statement`, `while_statement`, `try_statement`, or
`match_statement` at the outer scope. The reported location is the
first offending statement in source order.

### Exemptions

Five patterns look like control flow to a naive walk but read as linear
test code in practice and are not flagged:

- **`try` / `finally` without `except`** — pure cleanup, not branching.
  Only `try` blocks that contain at least one `except` clause fire.
- **`for` over asserts with optional intervening assignments,
  comments, bare non-helper calls, and `with` wrappers** — a
  parametrize-by-loop pattern (`for case in cases: assert case.ok`,
  `for m in months: s = compute(m); assert s == 0`, or `for case in
  cases: with self.subTest(...): self.assertX(...)`) where the loop
  body contains at least one assert-bearing statement, only plain
  assignments and inline `# comments` interleaved, optionally a
  trailing bare non-helper call statement (e.g.
  `ast.parse(case.content)` — no assignment, no `return`), optionally
  wrapped in `with` blocks whose bodies recursively satisfy the same
  shape, and no control flow at any nesting level. Helper-call asserts
  (`self.assertEqual(...)`) count alongside bare `assert`s. A loop
  body consisting entirely of bare calls with no real assert still
  fires.
- **`for` of pure side-effect calls inside an assertless test** —
  mis-named fixtures (functions whose name starts with `test_` but that
  contain no asserts anywhere) often use a loop to set up or tear down
  state. When the enclosing test body has zero asserts and the loop
  body contains only call statements or assignments (no control flow),
  the loop is treated as cleanup, not branching.
- **Control flow inside a nested `def` or `lambda` within the test** —
  the outer test's control flow is the only concern. An inline helper
  can have whatever structure it needs.
- **Runtime skip call as the first real body statement** — a test whose
  very first statement (after any leading docstring or comments) is a
  call to `self.skipTest(...)`, `self.skip(...)`, or `pytest.skip(...)`
  is treated as unconditionally skipped. Its body never executes, so
  structural smells are not flagged. Equivalent to
  `@pytest.mark.skip`-decorated tests. Note: `skipif`, bare `skip(...)`,
  and any other receiver are not matched.

## Positive example

```python
def test_branch():
    x = compute()
    if x > 0:           # ZR001 fires here
        assert x == 1
    else:
        assert x == -1
```

## Negative example

```python
import pytest

@pytest.mark.parametrize("x,expected", [(1, 1), (-1, -1)])
def test_branch(x, expected):
    assert compute(x) == expected
```

## Config

```toml
[tool.zorilla.rules.ZR001]
enabled = true
```

Set `enabled = false` to disable the rule project-wide. There are no
other knobs for ZR001.

## Suppression

Inline (offending line):

```python
def test_branch():
    if condition:  # zorilla: ignore[ZR001]
        ...
```

File-level (very first line of the file):

```python
# zorilla: ignore-file
```
