# ZR001 — conditional-test-logic

## Why

A pytest test should read as a linear "arrange / act / assert". Control-flow
constructs (`if`, `for`, `while`, `try`) hide intent, invite coverage holes,
and often smuggle two scenarios into one test. Extract the branches into
parametrized cases (`@pytest.mark.parametrize`) or separate test functions.

The rule fires once per test function whose body contains any
`if_statement`, `for_statement`, `while_statement`, or `try_statement` at
the outer scope. The reported location is the first offending statement
in source order.

### Exemptions

Three patterns look like control flow to a naive walk but read as linear
test code in practice and are not flagged:

- **`try` / `finally` without `except`** — pure cleanup, not branching.
  Only `try` blocks that contain at least one `except` clause fire.
- **`for` over bare or helper-only asserts** — a parametrize-by-loop
  pattern (`for case in cases: assert case.ok`) where every top-level
  statement of the loop body is `assert` or an assertion-helper call.
  Empty or non-pure for-loops still fire.
- **Control flow inside a nested `def` or `lambda` within the test** —
  the outer test's control flow is the only concern. An inline helper
  can have whatever structure it needs.

## Positive example

```python
def test_branch():
    x = compute()
    if x > 0:           # ZR001 fires here
        assert x == 1
    else:
        assert x == -1
```

## Negative example

```python
import pytest

@pytest.mark.parametrize("x,expected", [(1, 1), (-1, -1)])
def test_branch(x, expected):
    assert compute(x) == expected
```

## Config

```toml
[tool.zorilla.rules.ZR001]
enabled = true
```

Set `enabled = false` to disable the rule project-wide. There are no
other knobs for ZR001.

## Suppression

Inline (offending line):

```python
def test_branch():
    if condition:  # zorilla: ignore[ZR001]
        ...
```

File-level (very first line of the file):

```python
# zorilla: ignore-file
```
