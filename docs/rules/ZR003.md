# ZR003 — no-assertion

## Why

A test that never asserts never fails — it only exercises code for side
effects. Pytest treats the absence of an exception as success, so a test
with no check is green forever. Every test needs at least one observable
postcondition.

The rule fires once per test function whose body contains none of:

- a bare or message-bearing `assert` statement;
- a call whose function's final identifier is a known assertion helper
  (e.g. `assertEqual`, `fail`), configurable via `extra_helpers`;
- a call whose function's final identifier follows the snake-case
  assertion-helper convention — names starting with `assert_`
  (e.g. `assert_called_with`, `assert_css_class_present`) or `_assert_`
  (private helpers such as `_assert_invariant`). This shape is
  recognized unconditionally; you do not need to list these names in
  `extra_helpers`. The trailing underscore is required, so plain
  `assertion(x)` does **not** count;
- a `with <expr>.raises(...)` or `with <expr>.warns(...)` context manager;
- a `with does_not_raise():` context manager — the explicit no-exception
  contract, see below.

The walk descends into nested inline helpers. The finding points at the
test function's `def` line — the intent is "this whole test is
assertion-free".

Tests decorated with `@pytest.mark.skip` / `@pytest.mark.xfail` (at the
function or class level) are never flagged — the body never executes. The
same applies to tests whose **first real body statement** (after any
leading docstring or comments) is a runtime skip call:
`self.skipTest(...)`, `self.skip(...)`, or `pytest.skip(...)`. Such tests
are unconditionally skipped at runtime; the absence of assertions is by
design. Note: `skipif`, bare `skip(...)`, and non-`self`/`pytest`
receivers are not matched.

## Deliberate no-exception contracts

Some tests exist to prove an operation is safe to repeat, or safe on an
edge input, and their whole contract is "this does not raise". A dummy
`assert True` satisfies the rule without stating that contract. State
it instead with the idiom the pytest documentation uses for
parametrized raising:

```python
from contextlib import nullcontext as does_not_raise


def test_closing_an_already_closed_stream_is_safe():
    stream = io.StringIO()
    stream.close()
    with does_not_raise():
        stream.close()
```

`nullcontext` lets any exception propagate, so the test still fails when
the operation raises; the alias is what makes the intent readable, and
it is the alias the rule recognises. A bare `with nullcontext():` says
nothing and still fires: zorilla never guesses a contract from a test
name or a comment. Use the idiom only when not raising *is* the
contract. A test whose subject leaves observable state — a file
written, a spy called, a value returned — should assert on that state,
and the finding on such a test is correct.

## Positive example

```python
def test_does_nothing():       # ZR003 fires here
    setup()
    act()
```

## Negative example

```python
import pytest

def test_ok():
    assert value() == 1

def test_raises():
    with pytest.raises(ValueError):
        boom()
```

## Config

```toml
[tool.zorilla.rules.ZR003]
enabled = true
extra_helpers = ["expect", "verify"]
```

`extra_helpers` merges with the built-in unittest helpers. Matching is
by the final identifier of the call target, so `self.expect(...)` and
bare `expect(...)` both match.

## Suppression

Inline (on the `def` line, since that's where the finding is reported):

```python
def test_smoke():  # zorilla: ignore[ZR003]
    do_side_effect_only()
```

File-level:

```python
# zorilla: ignore-file
```
