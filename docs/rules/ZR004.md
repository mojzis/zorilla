# ZR004 — assertion-roulette

## Why

When a test has many bare `assert` statements about several things and
one of them fails, the reader has to work out which of the test's claims
broke, and every assert after it never ran — nothing is known about the
rest. That is assertion roulette, and it is the usual symptom of a test
that checks several behaviours at once. The fix is to split the test so
each one has a single subject, to add messages, or to collapse the
asserts into one richer assertion.

The rule counts bare `assert` statements (no message) per test and fires
when the count strictly exceeds `max_asserts`. Asserts with a message
(`assert x, "msg"`) are exempt — the message removes the ambiguity.

Tests decorated with `@pytest.mark.skip` / `@pytest.mark.xfail` (at the
function or class level) are never flagged. The same applies to tests
whose **first real body statement** (after any leading docstring or
comments) is a runtime skip call — `self.skipTest(...)`, `self.skip(...)`,
or `pytest.skip(...)`. Such tests are unconditionally skipped; their
bare-assert count is academic. Note: `skipif`, bare `skip(...)`, and
non-`self`/`pytest` receivers are not matched.

### A contract check about one subject is not roulette

Six bare asserts that are all about one record — `record.name`,
`record.enabled`, `record.count`, ... — are a contract check. Each
failing line names its field and pytest prints the values, so there is
nothing to reconstruct; the alternatives (a message that repeats the
field name, or six one-assert tests) cost maintenance without adding
information. Such tests never fire, whatever their count: `max_asserts`
measures sprawl across subjects, not length.

The subject is found structurally, never guessed from a name:

- the left operand of a comparison, or the **right** one for `in` /
  `not in` — the container is what is being checked;
- through `not`, unary minus, parentheses, `await`, and the left side of
  `and` / `or`;
- through attributes, subscripts and method calls down to the root name
  (`record.tags[0].lower()` is about `record`);
- into the first positional argument of a free function (`len(row)`,
  `float(row[2])`, `isinstance(row, tuple)` are about `row`);
- `self` and `cls` are namespaces, not subjects: `self.result.x` is
  about `self.result`, and `self.a` and `self.b` are two subjects.

A literal, a comprehension or a call without a positional argument has
no subject, so a table of `assert classify(1) == "one"` cases is not a
contract — it is `@pytest.mark.parametrize` material — and the threshold
applies. One assert about a second subject withdraws the exemption: a
test that checks two things is two tests.

**Split or keep?** Keep a run of bare asserts when they describe one
value the test produced. Split when they reach for different things —
the result, the mock, the log, the database — because a failure in the
third hides the state of the fourth, and each of those is a behaviour of
its own. When the asserts must stay together, give each a message that
says which claim it makes.

## Positive example

```python
def test_sprawl():
    result = run()
    assert result.ok            # 6 bare asserts about 5 subjects: fires here
    assert result.code == 0
    assert mock.call_count == 1
    assert log.lines == []
    assert db.rows == []
    assert clock.now == 0
```

## Negative examples

Six bare asserts, all about `record`:

```python
def test_record_contract():
    record = load()
    assert record.name == "demo"
    assert record.enabled is True
    assert record.count == 2
    assert record.tags == []
    assert record.mode == "safe"
    assert record.owner is None
```

Seven membership checks against one rendered report, the same way:

```python
def test_report_contract():
    report = render(usage)
    assert "--- Tokens & cost ---" in report
    assert "Cost: $0.18" in report
    assert "output $0.06" in report
    assert "cache read $0.05" in report
    assert "Tokens: 118,500 total" in report
    assert "input 1,500" in report
    assert "sidechain" not in report
```

The sprawling test, with a message on each assert:

```python
def test_sprawl_explained():
    result = run()
    assert result.ok, "run succeeds"
    assert result.code == 0, "exit code"
    assert mock.call_count == 1, "one upstream call"
    assert log.lines == [], "nothing logged"
    assert db.rows == [], "nothing persisted"
    assert clock.now == 0, "clock untouched"
```

Or collapsed into one comparison where the type supports it:

```python
def test_all_fields():
    result = load()
    assert result == User(
        name="alice", age=30, email="a@b", role="admin", active=True
    )
```

## Config

```toml
[tool.zorilla.rules.ZR004]
enabled = true
max_asserts = 4
```

`max_asserts` defaults to `4` — the rule fires on the 5th bare assert
about a second subject. Raise it when multi-subject asserts are the
convention in a suite and the finding count drowns out the rest; a
lower count is not by itself evidence of better tests.

## Suppression

Inline, on the **first** bare assert of the test — that is where the
finding is reported, and a directive on a later assert has no effect.
If that assert spans several lines, any line of it works:

```python
def test_sprawl():
    result = run()
    assert result.ok  # zorilla: ignore[ZR004] -- asserts stay together: one round-trip
    assert mock.call_count == 1
    ...
```

The anchor moves if that first assert gains a message or is removed, so
prefer the remedies above; a suppression is for the rare test whose
asserts must stay together and are about several subjects.
